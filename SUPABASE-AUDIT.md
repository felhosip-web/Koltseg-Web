# Supabase & Cloud Sync Audit (Deep Audit 3)

Ez a dokumentum a Költség Nyilvántartó alkalmazás felhő szinkronizációs rétegének (Supabase) és a hozzá kapcsolódó SQL / helyi logika részletes vizsgálatát és javításait tartalmazza.

## 1. Supabase SQL Séma és Adattípusok
Az adatbázis sémát a `supabase/migrations/20260712222340_init_schema.sql` definiálja.

**Talált hiba (ID típusok):**
A kezdeti séma `BIGINT` típusú azonosítókat használt több tábla (`items`, `templates`, `reminders`, `incomings`, `incoming_senders`) esetében. Eközben a frontend alkalmazás (v11 óta) mindenhol string formátumú `UUID`-ket (pl. `v4` UUID-ket generál és kezel) használ elsődleges kulcsként. Ez kritikus hibát okozott, mert a felhőbe történő szinkronizálás során típuseltérés lépett fel.

**Javítás:**
Módosítottam a `20260712222340_init_schema.sql` migrációs fájlt: az érintett táblákban (items, templates, reminders, incomings, incoming_senders) az `id` mező típusát `BIGINT`-ről `TEXT`-re cseréltem (mivel az UUID-k frontend oldalon stringként vannak kezelve, és a string/text típus a legkompatibilisebb). Ezzel elkerülhető a felhő oldali típuseltérés, amikor a frontend UUID-ket próbál pusholni. A `GENERATED BY DEFAULT AS IDENTITY` részt is eltávolítottam, mivel az azonosítókat mindig a kliens generálja és szolgáltatja (Offline-first / UUID megközelítés).

## 2. RLS (Row Level Security) Irányelvek
Az SQL sémában az RLS engedélyezve van minden táblára (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY`).

**Aktuális állapot:**
Jelenleg a rendszer egy "Mindenki elérheti" (Mindenki elérheti) policy-t használ minden táblára: `CREATE POLICY "Mindenki elérheti" ON table_name FOR ALL USING (true) WITH CHECK (true);`.
Mivel az alkalmazás Supabase kliens inicializálásánál a `persistSession: false` (vagy egyszerű anon/publikus kulcs) megközelítést használja (a user beállításaiból húzza be a kulcsot és az URL-t), ez a policy szükséges ahhoz, hogy a dedikált backend nélkül is működjön a szinkronizáció a felhasználó által megadott projektben. Bár ez nyitott hozzáférést ad ahhoz az egy specifikus Supabase adatbázishoz, az app kontextusában (ahol a user a saját Supabase kulcsát adja meg a kliensnek) ez elfogadható megoldás a könnyű beállítás érdekében.

## 3. Törlés (Delete) Logika és Árva Rekordok a Felhőben
**Probléma (Orphan Entries):**
Ha a felhasználó töröl egy kategóriát (`items`), a lokális adatbázis (`IndexedDB`) egy tranzakcióban törli a kategóriát és a hozzá tartozó tranzakciókat (`entries`). Azonban a felhő (Supabase) szinkronizáció során a rendszer külön-külön próbálta elküldeni a törlési parancsokat, és ha valami megszakadt, a felhőben ott maradhattak a "lebegő" tranzakciók (orphan entries), amelyeknek már nem volt érvényes kategóriájuk.

**Javítás (SQL Kaszkád Törlés):**
Kiegészítettem az SQL sémát egy kaszkád törlést végrehajtó triggerrel a Supabase oldalon.
```sql
CREATE OR REPLACE FUNCTION delete_item_cascade()
RETURNS TRIGGER AS $$
BEGIN
    DELETE FROM entries WHERE "cellKey" LIKE OLD.id || '\_%' OR "cellKey" LIKE '%\_' || OLD.id;
    RETURN OLD;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trigger_delete_item_cascade
AFTER DELETE ON items
FOR EACH ROW EXECUTE FUNCTION delete_item_cascade();
```
Így amikor a felhő megkapja a parancsot egy kategória (`items` tábla) törlésére, automatikusan (adatbázis szinten) kitörli a hozzá tartozó összes bejegyzést (amelynek `cellKey`-je utal a kategória ID-jére). Ez konzisztensen tartja a felhő adatbázist függetlenül a hálózati megszakadásoktól.

## 4. Soft-delete / Tombstone (deleted_records)
Az offline törlések kezelésére a rendszer a `deleted_records` táblát használja (tombstone pattern).

**Működés ellenőrzése:**
- Amikor a felhasználó töröl egy rekordot, az `oop-core.js` `delete()` metódusai beírnak egy bejegyzést a `deleted_records` táblába (id, record_id, table_name, deleted_at, updated_at).
- A szinkronizációs folyamat a `sync-service.js`-ben egyrészt letölti a táblákat (beleértve a `deleted_records`-ot is), majd az összefésülésnél (merge) a tombstone rekordok alapján törli a lokális adatbázisból is azokat a rekordokat, amiket egy másik eszközön töröltek.
- A logika stabilnak tűnik. A rendszer jól védi a tombstone rekordokat (amikor konfliktus van, azokat mindig alkalmazza).

## 5. Szinkronizációs (Sync) Sor és Queue Fallback
A Queue (`SyncService` queue) rendszert már a korábbi (Deep Audit 2) során javítottuk, hogy ellenállóbb legyen a megszakításokkal szemben.

- A `processQueue` sikeresen újrapróbálkozik (max 3-szor), ha hiba van.
- Az olyan hibáknál, mint a rossz adat (`unrecoverable: true`), eldobja a kérést, hogy a sor ne akadjon el.
- A core komponensek (`ItemManager`, `MonthManager` stb.) törlési metódusaiban (pl. `await this.db.delete()`) kötelező a `try/catch`, és ha a lokális törlés (vagy mentés) meghiúsul, a rendszer korábban meghívta a `this.syncService.clearQueue()` metódust. Ezt a mostani javítással eltávolítottuk: a queue csak akkor ürül, ha a Supabase felhő visszaigazolja a sikeres törlést. Helyi hiba esetén az elem bent marad a queue-ban későbbi próbálkozásra.

## Összegzés
- **Megoldva:** A Supabase UUID vs INT típusütközés az SQL migrációs szkriptben javításra került (`TEXT` típusúra cserélve).
- **Megoldva:** Az árva `entries` rekordok (kategória törlésénél) a felhőben mostantól adatbázis szintű triggerrel (kaszkád törlés) tisztítódnak.
- **Megoldva:** `parseInt` maradványok korábban eltávolításra kerültek, a string formátum a teljes flow-n keresztül támogatott.
- A Sync Queue és a Supabase Upsert / Delete logika megbízhatóan kezeli az offline módot.
